# Python を Rust へ移す順（測って並べた表。版 3.58.1・2026-11-01）

「Python が相当に優位な場合を除き、Rust に書き換える」ための下ごしらえ。文章の見立てではなく、測った数で順を決める。
数は `python program/tools/rust-port-bench.py --calibrate 20000` で出し直せる（下の数は Linux の開発機の 1 回分。Windows の数は CI の記録から）。

## 1. いまの形（先に分かったこと）

- Flask は版 3.8.0 で外してある。Python のアプリは**標準の部品だけ**で動き、pip で入れる物は無い（同梱の Python にも無い）。
  → 「Python にしか無い部品があるから Python が優位」という理由は、どの部品にも無い。
- Python のアプリ（`program/app`）は 67 ファイル・**14,306 行**（空行・注釈・説明文を除く）。業務の部品 10,401 行と、道（routes）・枠（web.py・版の履歴など）3,905 行。試験は 11,544 行。
- Rust（`desktop/`）が受け持つのは、窓・起動と更新・静的ファイル・品質の一覧（`lotlist.rs`）と写し（`mirror.rs`）。
- Rust の一覧は、**計算列・ロット番号の列の上書き・結合・タブの権限**を持たない。そのたびに Python へ戻している
  （画面が `engine=python` を付ける〈`lotlist.js:348`〉・設定の答えの係を `python` にする〈`routes/lotlist.py:117`〉）。Python を外すには、まずこの穴を埋める。

## 4. 移す単位と順

部品を、いっしょに動く物ごとに 6 つの単位と枠に分けた（全 39 部品が、どれか 1 つの単位に入る）。

| 順 | 単位 | 部品 | 行 | 試験 | 縮みうる時間（上の表から） | 新しく要る crate | 決めた理由 |
|---:|---|---|---:|---:|---|---|---|
| 1 | **式（計算列）** | formula・num_expr | 1,093 | 31 | 単独では 0（下の 2〜4 の前提） | regex（fancy-regex）・unicode-normalization | 依存の葉（使う部品 0）。いちばん小さく、画面との突き合わせの表（`formula-parity`・`num_expr_cases.json`）が既にある。これが無いと、計算列のたびに一覧・集計・ダッシュボードが Python へ戻る |

順の決め方: ①依存の葉から（使う部品を先に移さないと、移した部品が Python に尋ね返す）、②その中で「縮みうる時間 ÷ 移す量」が大きい物から、③速さの利点が無い物（5〜7）は、Python を外すために最後にまとめて。

### Python が相当に優位な所はあるか

| 見た所 | 判定 |
|---|---|
| 外の部品（ライブラリ） | 無い（標準の部品だけ）。Python の優位にならない |
| 利用者が式に書く正規表現（JavaScript の書き方。後方参照 `\1`・`\k<名前>` も） | Rust の regex は後方参照・先読みを持たない。**fancy-regex で代えられる**（重い形を断る決まり `regex_risk` は今と同じに残す）。優位とまでは言えない |
| HTML を読む（LotDsp・CM3） | いまも正規表現と `html` の標準の部品で読んでいる。Rust でも同じ形で書ける |
| **作る・確かめる道具** | **ここは Python が優位**。開発用サーバー（`ui_server.py`）・撮影と採点の道具（`ui-*.mjs`）・試験の作り物は、いま Python のアプリを起こして動く。アプリを Rust にしたら、道具が起こす先を Rust のサーバーに替える。それまでは、前例と同じく **Python を「答えの見本」（オラクル）として残し**、同じ問い合わせで同じ答えかを突き合わせる |

→ アプリの中身について「Python が相当に優位」な所は見つからなかった。ただし移す量は合わせて 14,306 行・試験 11,544 行。1 単位ずつ、突き合わせの試験で同じ答えを示してから入れ替える（版 2.1.0・2.2.0 と同じ）。

## 5. 分からないこと

- 利用者の PC（同梱の Python・ウイルス対策）での起動の時間と、ZIP の中の Python の大きさ（測っていない）。
- ダッシュボード・集計を Rust にしたときの実際の速さ（見積もりは「手を 0 にした下限」の 0.7〜1.7 倍。一覧でしか確かめていない）。
- どの画面がどれだけ使われているか（使われ方の重みは付けていない。ダッシュボードが最初の画面であることだけは確か）。

## 7. 進み具合

### 順 1: 式（計算列）— 版 3.59.0 で移した

- 移し方は 6 案を比べ、別のエージェントが試作を組み直して測ったうえで採点して決めた（`program/tools/ui-proposals/2026-11-formula-port.json`。
  1 位 F「素直に移し、事例表を 3 つの約束にする」85.5 点。画面の JavaScript を Rust の中で動かす案〈QuickJS〉は、字・日付の式で今の Python より遅かった）。
- `desktop/src/formula.rs`: 字句・構文・評価・JavaScript の正規表現の読み替え（fancy-regex。`\d`・`\w`・`\b` は英数字だけ）・置き換えの `$1`・変換表（conv）・日時・釜番・
  計算列（表示名とほかの式の列を 1 段たどる）・SQLite の関数として登録する係。字は JavaScript と同じく UTF-16 の単位で持つ（切り出しで生まれる片割れのサロゲートも同じ答え）。
- 事例表 `program/tests/fixtures/formula_cases.json`（4,416 件。画面の答えを node で焼き付けた物）を、Rust（`cargo test --test formula_cases`）と
  Python（`tests/test_formula_parity.py`）が node 無しで読む。中身は書いた例・作った例 1,500・変換表のプリセットと全部の条件（nends・ncontains・filled・含まない範囲など）・
  作った後の採点で別のエージェントが画面の答えを出して確かめた事例（比べ方・置き換えの `` $` ``・`.` と改行・正規表現の書き方の隅・組の名前・後方参照・`[]` の範囲・先読みの繰り返し）。
- 試験が甘くないかは、誤りをわざと入れて確かめた。1 回目の作った後の採点（71.7 点）で、別のエージェントが入れた 9 つのうち 4 つ（`<=` を `<`・`` $` `` を後ろの字・
  `.` が `\r` にも当たる・変換表の nends を ends と同じ）を見逃していた。事例表の穴を埋めた後は 9 つとも食い違いとして見つける。
- 同じ採点で、画面と答えが違う正規表現の書き方も見つかった（Rust: `\00`。Rust と Python: 画面が断る `(?i)`・`(?#…)`・`(?P<…>)`・`a++`・`(?>…)` を読んでいた・
  組の無い `\1` と `\8`。Python だけ: `a*?` の置き換え・`[\d-z]`）。Rust と Python の読み替えを、画面（JavaScript の Annex B）と同じ決まりにそろえた。
- 2 回目の作った後の採点（77.5 点）で、さらに細かい隅が見つかった（`\b+`・`[a--b]`・同じ組の名前・数字で始まる組の名前・先読みと空の組の繰り返し・
  名前付きの組が無いときの `\k<n>`・前を指す `\1(a)`・合っていない組への `\1`・`[\c1]` など）。Rust と Python の読み替えを組み直した:
  組は番号だけで持ち名前は対応で引く・後方参照は「閉じた組なら、合っていれば同じ字・合っていなければ空、閉じていなければ空」・`[]` の中は JavaScript と同じに範囲を組む・
  直前の種類（字・繰り返し・\b のような位置・先読み・後読み・空の組）で繰り返しを決める。自分で入れた誤り 12 のうち 11 を見つけ、残り 1 つ（逆の範囲を断らない）は
  Rust の regex 自身も断るので答えに出ない。
- 3 回目の作った後の採点は 81.3 点で、合格点（80 点）以上（71.7 → 77.5 → 81.3）。残る違いは、正規表現の仕組み（fancy-regex・Python の re）が JavaScript と違う所
  （繰り返しの中の組が回るたびに空に戻る・長さの決まらない後読み・空に合った回で繰り返しを止める・(?:^)+）で、直さずに `formula.rs`・`formula.py` の「合わない所」に書いた。
- Rust の一覧（`lotlist.rs`）は計算列で並べ替える問い合わせ（`calc`）にも答える。画面は `engine=python` を付けなくなった。変換表は一覧の設定の答え
  （`/api/lotlist/settings` の `conversions`）で受け取り、中身の目印（`MasterStore.stamp`）が変わったときだけ読み直す。
  Python の答えとの突き合わせ（`desktop/tests/lotlist_parity.rs`）に計算列の 8 通り（四則・条件・字・正規表現・日付・変換表・表示名とほかの式・読めない式・まとめ・鍵の形）を足した。
- 速さ（品質 20,000 行・計算列で並べ替えた 1 ページ・中央値。`rust-port-bench.py --calibrate 20000`）:

| 式 | Python | Rust | 速さの比 |
|---|---:|---:|---:|
| 四則 `[重量] * 2 + 1` | 98 ms | 33 ms | 3.0 倍 |
| 条件 `if([重量] > 3000, '重', '軽')` | 95 ms | 26 ms | 3.7 倍 |
| 字 `left([ロット番号], 3) + '-' + upper([合金])` | 291 ms | 125 ms | 2.3 倍 |

  字の答えの式が「Python の手を 0 にした下限」（26・49 ms）より遅いのは、字で並べる手間（SortKey が字を数に読めるか調べる）が Rust でも約 69 ms かかるため

  字で並べる手間を縮めるのは、移すのとは別の改良として残す。
- 途中で見つけて直した物: 手元のみの PC（共有の置き場が無い）で変換表を直しても、計算列の並べ替え・ダッシュボードの集計が直す前の表のままだった
  （読み直すかを版の番号で決めていたが、手元のみの PC では書いても版の番号が増えない）。中身の目印（`MasterStore.stamp`）で決めるように直し、`tests/test_conversions.py` に試験を足した。
- Python の式（`services/formula.py`）は、集計・ダッシュボード（順 3・4）が Python にある間は使い、Rust へ移したあとは事例表の答え合わせの相手としてだけ残る。

### 順 2: 一覧の道（品質・実績・仕掛・足した元・結合した表）— 版 3.60.0 で移した
