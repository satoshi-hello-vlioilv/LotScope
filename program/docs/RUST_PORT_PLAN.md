# Python を Rust へ移す順（測って並べた表。版 3.58.1・2026-11-01）

「Python が相当に優位な場合を除き、Rust に書き換える」ための下ごしらえ。文章の見立てではなく、測った数で順を決める。
数は `python program/tools/rust-port-bench.py --calibrate 20000` で出し直せる（下の数は Linux の開発機の 1 回分。Windows の数は CI の記録から）。

## 1. いまの形（先に分かったこと）

- Flask は版 3.8.0 で外してある。Python のアプリは**標準の部品だけ**で動き、pip で入れる物は無い（同梱の Python にも無い）。
  → 「Python にしか無い部品があるから Python が優位」という理由は、どの部品にも無い。
- Python のアプリ（`program/app`）は 67 ファイル・**14,306 行**（空行・注釈・説明文を除く）。業務の部品 10,401 行と、道（routes）・枠（web.py・版の履歴など）3,905 行。試験は 11,544 行。
- Rust（`desktop/`）が受け持つのは、窓・起動と更新・静的ファイル・品質の一覧（`lotlist.rs`）と写し（`mirror.rs`）。
- Rust の一覧は、**計算列・ロット番号の列の上書き・結合・タブの権限**を持たない。そのたびに Python へ戻している
  （画面が `engine=python` を付ける〈`lotlist.js:348`〉・設定の答えの係を `python` にする〈`routes/lotlist.py:117`〉）。Python を外すには、まずこの穴を埋める。

## 2. 測り方（評価関数 `tools/rust-port-bench.py`）

| 測る物 | 中身 |
|---|---|
| 棚卸し（読むだけ） | 部品ごとの行・試験（その部品を読む試験ファイルの test_*）・使う部品と使われる部品・依存の段（葉＝0）・要る crate（Cargo.toml に有れば済）・Python の re にしか無い書き方 |
| 速さ | 開発用サーバーと同じ試験データ（`ui_server.build`）を品質 20,000 行・作業実績 12 台 × 2,000 行・仕掛 20,000 ロットにして、引数の無い GET の全部・データ元ごとに画面と同じ 6 つの問い合わせ（一覧・まとめ・検索・カラムの札・スライサー・集計。列はカラムの札の答えから選ぶ）・ダッシュボードの組み込みの全パネル（控えを空にした冷えた形）を 5 回の中央値で |
| 時間の内訳 | 1 回を cProfile の下で呼び、**SQLite の中・JSON に書く・Python の手**に分ける。Rust に移して縮むのは Python の手だけ（SQLite の中は Rust でも同じ） |
| 見積もりの確かめ | 既に Rust にある一覧で、Python の時間・Python の手の割合・Rust の実際の時間（`desktop/examples/lotbench.rs`）を並べる |
| Python を通す手間 | 中身（sidecar.py）を窓と同じ形で起こして ready まで・枠 1 往復 |

### 見積もりの確かめ（品質 20,000 行・中央値 ms）

| 問い合わせ | Python | Python の手 | 手を 0 にした下限 | Rust（実際） | 速さの比 |
|---|---:|---:|---:|---:|---:|
| 1 ページ目（500 行） | 18 | 64% | 6 | 8 | 2.3 倍 |
| 検索「汚れ」（全列） | 459 | 58% | 192 | 217 | 2.1 倍 |
| 条件 2 つ | 42 | 52% | 20 | 14 | 3.0 倍 |
| 並べ替え | 38 | 52% | 18 | 18 | 2.1 倍 |
| まとめる＋並べ替え | 245 | 16% | 207 | 143 | 1.7 倍 |
| 数で絞る | 50 | 73% | 13 | 21 | 2.4 倍 |
| 0 件（日付の手がかり） | 234 | 87% | 31 | 51 | 4.6 倍 |

Rust の実際の時間は「手を 0 にした下限」の 0.7〜1.7 倍に収まった。**Python の手の割合は、移して縮む量の物差しに使える**（cProfile は Python の関数ごとに手間を足すので割合は多めに出る。上限として読む）。

## 3. 速さ（品質 20,000 行・作業実績 12 台 × 2,000 行・仕掛 20,000 ロット。中央値 ms）

| 道の集まり | 道 | 合計 | SQLite の中 | Python の手 | いちばん遅い道 |
|---|---:|---:|---:|---:|---|
| ダッシュボード | 11 | 763 | 224（29%） | **538（70%）** | 設備ごとの仕掛と前日の実績 163 |
| 足したデータ元（仕掛・マスタ・スケジュール） | 25 | 736 | 492（67%） | 235（32%） | 仕掛のカラムの札 308（SQLite 84%） |
| 品質 | 6 | 476 | 162（34%） | 302（64%） | まとめ 206 |
| 実績 | 7 | 183 | 21（12%） | **158（87%）** | まとめ（日・直ごとの数）126 |
| マスタ・設定・権限など（ほか 10） | 28 | 22 | 0 | 21 | 設備グループ 7.5 |

- 集計（`/pivot`）は 6 本で 198 ms のうち **182 ms（92%）が Python の手**。ダッシュボードの中身も集計なので同じ形。
- マスタ・設定の道は 28 本を足しても 22 ms。**Rust にしても体感は変わらない**（移すのは Python を外すため）。
- カラムの札（`fields=1`）は SQLite の中が大半（仕掛 84%）。**Rust にしても縮まない**。速くするなら問い合わせ（列ごとの DISTINCT）の作りを変える（移すのとは別の改良）。

### Python を通す手間

| | Linux（開発機） | Windows（CI・`desktop.yml` の記録・版 3.58.0） |
|---|---:|---:|
| 中身が答えられるまで | 187 ms | **1,099 ms**（spawn_ms） |
| 枠 1 往復 | 0.13 ms（中で呼ぶと 0.03 ms） | 分からない |

- 枠の往復は 0.1 ms ほどで、問い合わせ 1 本の重さに比べて小さい。**移す利点は枠ではなく、Python の手の時間と、起動の 1 秒余り**。
- 利用者の PC（同梱の Python・ウイルス対策）での起動時間は**測っていないので分からない**。CI より長いことはあり得る。
- 配る ZIP は 528 ファイル・9.3 MB（版 3.58.0）。そのうち同梱の Python がどれだけかは測っていない。

## 4. 移す単位と順

部品を、いっしょに動く物ごとに 6 つの単位と枠に分けた（全 39 部品が、どれか 1 つの単位に入る）。

| 順 | 単位 | 部品 | 行 | 試験 | 縮みうる時間（上の表から） | 新しく要る crate | 決めた理由 |
|---:|---|---|---:|---:|---|---|---|
| 1 | **式（計算列）** | formula・num_expr | 1,093 | 31 | 単独では 0（下の 2〜4 の前提） | regex（fancy-regex）・unicode-normalization | 依存の葉（使う部品 0）。いちばん小さく、画面との突き合わせの表（`formula-parity`・`num_expr_cases.json`）が既にある。これが無いと、計算列のたびに一覧・集計・ダッシュボードが Python へ戻る |
| 2 | **一覧の道をそろえる** | lot_list（Rust に有り）・work_summary・data_join・work_log・data_sources | 1,351 | 406 | 実績・仕掛・足した元の一覧 約 225 ms ＋ Python へ戻る分 | uuid | `lotlist.rs` が既にあり、足すのは「どのファイルを読むか」・作業のまとめ（日・直）・ロット番号の列の上書き・結合した表を読むこと。前例（版 2.1.0）と同じ突き合わせの試験で確かめられる |
| 3 | **集計** | pivot・aggregate・shifts・pivot_presets・display_formats | 1,256 | 188 | 集計 182 ms（92%） | なし | Python の手の割合がいちばん高い。1・2 を使う |
| 4 | **ダッシュボード・稼働** | dashboard・operation・equip_groups・card_forms | 1,193 | 153 | 538 ms（70%）。**最初の画面** | なし | 縮みうる時間がいちばん大きい。3 を使う（段 4） |
| 5 | **マスタ・権限・使用の履歴** | master_store・master_repository・access・presence・path_settings ほか 16 | 3,184 | 1,218 | 21 ms（速さの利点はほぼ無い） | hostname・glob・percent-encoding | いちばん大きく、試験もいちばん多い。速さでなく Python を外すために移す。1〜4 が Rust になっても、設定とマスタを Python に尋ねる間は Python が要る |
| 6 | **外とのつなぎ** | lotdsp_direct（見えない Edge を CDP で）・lotdsp_api・lotdsp_progress・lotdsp_link・cm3_schedule・schedule・calculator | 2,324 | 191 | 測れない（社内のサーバー待ちが主） | tungstenite・ureq・html-escape・base64 | 速さの利点は無い。WebSocket・HTTP の crate が要る。相手（LotDsp・CM3）が無い所では試せないので、作り物の相手（`schedule_fixture` など）を Rust の試験にも使う |
| 7 | **枠** | routes（道 126 本）・web.py・version（更新履歴）・boot・sidecar | 3,905 | — | 起動 1 秒余り・同梱の Python | — | 1〜6 が済めば道は Rust の振り分け（`router.rs`）へ。ここで初めて Python を同梱しなくてよくなる |

順の決め方: ①依存の葉から（使う部品を先に移さないと、移した部品が Python に尋ね返す）、②その中で「縮みうる時間 ÷ 移す量」が大きい物から、③速さの利点が無い物（5〜7）は、Python を外すために最後にまとめて。

### Python が相当に優位な所はあるか

| 見た所 | 判定 |
|---|---|
| 外の部品（ライブラリ） | 無い（標準の部品だけ）。Python の優位にならない |
| 利用者が式に書く正規表現（JavaScript の書き方。後方参照 `\1`・`\k<名前>` も） | Rust の regex は後方参照・先読みを持たない。**fancy-regex で代えられる**（重い形を断る決まり `regex_risk` は今と同じに残す）。優位とまでは言えない |
| HTML を読む（LotDsp・CM3） | いまも正規表現と `html` の標準の部品で読んでいる。Rust でも同じ形で書ける |
| **作る・確かめる道具** | **ここは Python が優位**。開発用サーバー（`ui_server.py`）・撮影と採点の道具（`ui-*.mjs`）・試験の作り物は、いま Python のアプリを起こして動く。アプリを Rust にしたら、道具が起こす先を Rust のサーバーに替える。それまでは、前例と同じく **Python を「答えの見本」（オラクル）として残し**、同じ問い合わせで同じ答えかを突き合わせる |

→ アプリの中身について「Python が相当に優位」な所は見つからなかった。ただし移す量は合わせて 14,306 行・試験 11,544 行。1 単位ずつ、突き合わせの試験で同じ答えを示してから入れ替える（版 2.1.0・2.2.0 と同じ）。

## 5. 分からないこと

- 利用者の PC（同梱の Python・ウイルス対策）での起動の時間と、ZIP の中の Python の大きさ（測っていない）。
- ダッシュボード・集計を Rust にしたときの実際の速さ（見積もりは「手を 0 にした下限」の 0.7〜1.7 倍。一覧でしか確かめていない）。
- どの画面がどれだけ使われているか（使われ方の重みは付けていない。ダッシュボードが最初の画面であることだけは確か）。
